# 07 MILo（Phase 6 / 参照研究の適用）

実施日: 2026-10-20 / ブランチ: `claude/T7-research` / 環境: WSL2 Ubuntu、torch 2.8.0+cu128、RTX 5060 Ti（sm_120）
対象: [MILo](https://github.com/Anttwo/MILo)（Inria/MPII系の非商用研究ライセンス）。公式コードは `~/ext/MILo` に置いて**無改変で実行**した（プロジェクトには取り込まない）。課金APIは使っていない。

## 1. 結論

| 対象 | 結論 |
|---|---|
| キャラ | **法線の精度が大きく上がる**（正解メッシュとの角度誤差の中央値 26° → **10°**）。ガウシアン数は 24万 → 7.3万と少なく、見た目は素の3DGSと同等。ただし抽出メッシュは Tripo の元メッシュより**重い**（194万面 対 144万面）ので「軽いプロキシメッシュ」にはならない |
| 背景 | **見た目は元の背景を忠実に再現したが、黒点・池の透過などの欠点は直らなかった**（自己蒸留なので入力の欠点を引き継ぐ）。法線は少し良くなった（陰影の当てはまり R² 0.11 → 0.17）。抽出メッシュは**918万面で、そのままはゲームに使えない**。ただし地面の高さは World Labs 付属のコライダーと一致した |

- 取り込む価値があるのは **「面の整合を学習中に入れて法線を安定させる」考え方**（Delaunay＋SDF でメッシュを学習ループに入れる）。法線が取れると、キャラ側の再ライト・接地影・背景の陰影分離（Phase 4 の課題）に使える。
- 公式コードをそのまま学習パイプラインに入れる選択は、速度（キャラ約70分、背景約2時間）とライセンスの面で取らない。必要なら考え方だけを自前実装する（9章）。

## 2. 手順（再現可能）

1. キャラのデータ: `scripts/blender/render_char_dataset.py` で144視点（T5の照明）、`scripts/gaussian/flatten_colmap_dataset.py`（黒背景に合成）と `write_colmap_bin.py`（COLMAP の .bin に変換）。
2. 背景のデータ: World Labs の背景3DGSには元の多視点写真がないので、**背景3DGSをKIRIで160視点に描画し直した画像を教師画像にした（自己蒸留）**。`scripts/blender/render_bg_dataset.py`（元カメラの周りの自由空間に乱数でカメラを散らす、1024×768）。
3. 環境と実行: `scripts/wsl/setup_milo.sh`、`build_milo.sh`、`rebuild_tetra.sh`、`run_milo.sh`（`IMP=outdoor run_milo.sh bg_scene_rgb --data_device cpu`）。MILo 付属の nvdiffrast は OpenGL(EGL) を使うが WSL に EGL がないため、`milo_shim.py`（公式コードを書き換えずに `RasterizeGLContext` を CUDA 版に差し替えて実行する）を経由。
4. 描画: `scripts/blender/render_scene_char_ply.py`（キャラ）、`render_bg_ply.py`（背景。T5と同じ5視点）。
5. 評価: `scripts/gaussian/eval_normals.py`、`eval_mesh_chamfer.py`、`eval_bg_mesh.py`、`scripts/lighting/lambert_compare.py`。

## 4. 背景の結果

同じ5視点で、元の背景（左）と MILo で学習し直した背景（右）を描画して比べた（`render_bg_ply.py`）。

- **正面ワイド**（[図](img/07-milo-bg-front.jpg)）、**木漏れ日ローアングル**（[図](img/07-milo-bg-dappled.jpg)）: 構図・色・光の筋ともほぼ同じ。MILo のほうが**やや甘い（ぼやける）**。
- **池まわりのクローズアップ**（[図](img/07-milo-bg-pond.jpg)）: 元の背景と同様、水面に**黒点**が残る。近くの岩・苔は MILo のほうがぼやける。
- **高い視点**（[図](img/07-milo-bg-oblique.jpg)）: 池の透過感や、右側の石段まわりの針状のにじみは、**どちらにも残る**。水面の黒点は MILo のほうがやや目立つ。

結論として、この方法（自己蒸留）では、**元の背景の欠点は直らない**。教師画像（元の背景の描画）に欠点が含まれており、MILo はそれを忠実に学習するため。欠点を直すには、欠点のない教師画像が要る（元の画像生成AIの参照画像から作り直す、または別の手法で整える）。

### 4.1 法線の質（陰影の当てはまり）

T5 の太陽方向測定（`measure_sun.py`）と同じ方法で、背景ガウシアンの法線（最小スケール軸）から、輝度を `L = A + B·max(0, n·l)` に当てはめて R² と太陽方向を測った（`lambert_compare.py`）。

| 条件 | 元の背景 R² / 太陽（方位, 仰角） | MILo R² / 太陽（方位, 仰角） |
|---|---|---|
| 全体 | 0.11 / (60°, 75°) | **0.17** / (20°, 40°) |
| 壁面（\|nz\|<0.6） | 0.03 / (295°, 5°) | **0.11** / (30°, 45°) |
| 近距離（<5m） | 0.05 / (285°, 25°) | **0.15** / (35°, 35°) |
| 中距離（5〜12m） | 0.02 / (110°, 55°) | 0.04 / (225°, 0°) |

- 元の背景は、条件ごとに太陽方向がばらばら（方位60〜295°）で、実際の太陽（白い光源は方位46°、仰角40°）と結びつかない。MILo は全体・壁面・近距離の**3条件で方位20〜35°、仰角35〜45°にそろい**、実際の太陽方向に近づいた。
- ただし R² は最大でも 0.17 で、**背景の焼き込み照明を法線から分離（再ライト）できる水準ではない**。背景の明暗は法線だけでなく、遮蔽・空光・照り返し・木漏れ日の影で決まるため。結論は T5 と同じで、**背景は焼き込み固定、キャラ側を合わせる**方針を変えるほどではない。

### 4.2 抽出メッシュ（ゲーム用の地面・コライダー）

`eval_bg_mesh.py` の結果（`experiments/T7/runs/milo_bg/mesh_eval.json`）:

| 項目 | MILo メッシュ | World Labs コライダー（`forest_clearing_collider.glb`） |
|---|---|---|
| 頂点／面 | 462万／**918万** | 8.2万／16万 |
| キャラ足元（0.4, 0）の地面高さ | **0.145 m**（5〜95%: 0.105〜0.195） | 0.122 m（該当三角形が1枚のみ） |
| 地面格子（0.5m）の高さ 中央値 | 0.45 m | 0.52 m |
| 小さな浮遊成分（100面未満） | 3,659個（全体の約1.4%の面） | 269個 |

- **MILo の足元の地面高さ 0.145 m は、T4/T5 で測った背景スプラットの地面（0.13〜0.17 m）と一致**し、統合シーンで置いている `CHAR_GROUND_Z = 0.13` と矛盾しない。
- World Labs のコライダーも**同じ座標系で重なる**（背景スプラットと同じ変換で一致）ことを確認した。疎だが、**地面の高さは MILo と近い**（0.52 対 0.45 m、傾斜・段差を含む）。T5 の「コライダーは疎で未検証」は、**座標系と地面高さの面では妥当**と確認できた。
- したがって、**衝突判定用の地面は World Labs のコライダーで足りる**。MILo の918万面メッシュは重すぎ、浮遊成分もあるため、そのまま使わない。使うなら大幅な簡略化（100万面以下）が必要。

## 5. つまずきと対処（公式コードは書き換えていない）

| 問題 | 原因 | 対処 |
|---|---|---|
| submodule のクローンが止まる | SSH の URL（公式の `.gitmodules`） | git のグローバル設定で `insteadOf` により HTTPS に書き換え。必要なのは nvdiffrast だけ（Depth-Anything は任意で省略） |
| ラスタライザ／simple-knn のビルドで `FLT_MAX`、`uint32_t` 未定義 | 新しい CUDA/gcc では標準ヘッダーの暗黙のインクルードがない | `NVCC_PREPEND_FLAGS="-include cfloat -include cstdint"` |
| `tetra_triangulation` のビルドで cmake のポリシーエラー、`torchCheckFail` 未定義 | cmake が古い書式、ABI フラグの固定（0）が torch 2.8 と不一致 | `CMAKE_POLICY_VERSION_MINIMUM=3.5` と Release フラグの上書きで再ビルド（`rebuild_tetra.sh`） |
| `points3D.bin` がなく学習が始まらない | 自作の COLMAP データに含めていなかった | `write_colmap_bin.py` で作成 |
| nvdiffrast の GL コンテキストが作れない | WSL に EGL がない | `milo_shim.py` で CUDA コンテキストに差し替え（書き換えは公式側にない） |

## 6. このプロジェクトへの効き目

| 課題 | 効き目 | 理由 |
|---|---|---|
| 法線が不安定（最小スケール軸） | ◎（キャラ）／○（背景） | キャラで 26°→10°。背景は R² 0.11→0.17 で、太陽方向が実際の方向に近づく |
| キャラの輪郭がくっきり（切り抜き感） | ○ | 柔らかい輪郭で背景と混ざる（3DGS一般の効果。MILo固有ではない） |
| 背景の黒点・針状スプラット・池の透過 | ✕ | 自己蒸留では教師画像の欠点を引き継ぐ |
| 背景の焼き込み照明・二重ライティング | △ | 法線が少し良くなるが、再ライトできる水準にはならない |
| 衝突判定用の地面 | △ | 地面の高さは合うが重い。World Labs のコライダーで足りる |

## 7. 自前実装へ持ち帰る候補

1. **法線の安定化**: ガウシアン最適化中に、近傍ガウシアンの法線の整合（隣り合う面が同じ向き）を正則化として足す。MILo の「メッシュを学習ループに入れる」は重いので、**法線整合の正則化だけ**を小さく実装するのが現実的（背景の針状スプラット対策にもなる）。
2. **キャラのProxy Mesh**: Tripo のメッシュを正解にして、ガウシアンをメッシュ面に結びつける（Frosting の方向。[07-frosting.md](07-frosting.md)）ほうが筋がよい。MILo の抽出メッシュは重く、使い道はない。
3. **背景の欠点の根治**: 外れ値（黒点・針状）の剪定を自前で書く（不透明度が高く、色が周囲と大きく違い、スケールが細長い、など）。教師画像が同じ欠点を持つので、MILo ではなく**元の背景PLYを直接直す**。
