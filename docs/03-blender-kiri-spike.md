# 03 Blender + KIRI 描画スパイク（T3）

実施日: 2026-10-20 / ブランチ: `claude/T3-blender-base` / 環境: Blender 5.2.1 LTS、RTX 5060 Ti、Windows 11
目的: 3DGSとメッシュの統合（遮蔽・影・ライト反応）の方式を決めるための実機検証。課金APIは使っていない。

## 1. 結論

| 項目 | 結果 |
|---|---|
| KIRI Engine 3DGS Render の Blender 5.2 対応 | **対応**。v5.1.0（2026-08-26）が「5.1.1 と 5.2.0 LTS で動作確認済み」と明記。5.2.1 LTSで有効化・描画とも問題なし |
| ヘッドレス（`blender -b`）での描画 | **可能**。`gpu.init()` を呼べばGPUオフスクリーン描画が通る。GUI不要でバッチ化できる |
| 3DGSとメッシュの前後関係（遮蔽） | **正しく動く**。メッシュ→ガウシアン、ガウシアン→メッシュの両方向を確認 |
| ライト反応 | **動く**。Blenderのライトの色・強さ・位置に応じてガウシアンの色が変わる。ただし「焼き込み色に係数を掛ける」近似で、物理的な再ライティングではない |
| 影 | メッシュ→ガウシアン、ガウシアン→メッシュとも**動く**（近似）。ガウシアン同士の自己影は未検証 |
| 規模・速度 | 公開サンプル（78.6万ガウシアン、SH3）が取り込み6.4秒、描画3.2秒（RTX 5060 Ti、960×720） |
| SPZ→PLY変換 | 自前実装が公開サンプルで正しく動作。KIRIで正立・正色で描画できた |

統合とライティングの設計への含意は5章にまとめた。

## 2. 導入と接続

- **Blender MCP**: `.mcp.json` に `uvx blender-mcp==1.9.1` を設定。ポートは **9877**（CatAnime側のBlenderが既定の9876を使うため分離）。
  アドオン1.6とサーバー1.9.1はプロトコルバージョン5で一致し、`get_addon_info` / `execute_code` の応答を確認した。
  GUIのBlenderは `scripts/blender/launch_blender_mcp.ps1` で起動する。Claude側のblenderツールはセッション再起動後に出る。
  接続確認は `BLENDER_PORT=9877 python scripts/blender/mcp_client.py handshake`。
- **KIRI導入**: `scripts/blender/install_kiri_addon.ps1`。公式GitHubリリースv5.1.0（約770MB、Gitには入れない）を、
  `%LOCALAPPDATA%\3DGSAnimation\blender-ext`（`BLENDER_USER_EXTENSIONS`）へ入れる。ユーザー共通のBlender設定は触らないので、他プロジェクトのBlenderには影響しない。
  導入前にコードを走査し、ネットワーク通信やプロセス起動の処理がないことを確認した（`socket` はノードのソケットのみ）。ライセンスはGPL-2.0-or-later。
- 代替案（旧版Blender併用など）は不要だった。

## 3. SPZ→PLY変換

`scripts/gaussian/spzply.py`（自前実装。Nianticの仕様記述を参考にしただけで、コードは流用していない）。

- 読み: SPZ v2/v3（gzip）、v4（zstd分割。`pip install zstandard` が必要、v4実ファイルでの検証は未実施）。書き: v2/v3。PLY読み書き。
- 座標系: 標準ファミリ（L/R, U/D, F/B の8種）を軸反転で相互変換。位置・回転・SHの符号を同時に変換する。SPZ既定はRUB、3DGSのPLYはRDF。
  回転ファミリ（Y/Z入替）とSH4次の反転は未対応。
- テスト `scripts/gaussian/test_spzply.py`（マイルストーン単位）:
  - 往復（v2/v3 × SH0〜3）が量子化誤差内で一致。
  - 座標系変換後も、共分散（楕円体の形）とSH評価（視線方向ごとの色）が元と一致。
  - 公開サンプル `hornedlizard.spz`（v2、78.6万点、SH3）を読み、PLY経由で往復。
- 実機確認: サンプルをRDFのPLYにして、KIRIに取り込み、オブジェクトを X軸 −90° 回転すると、Z上の正立した像になった（`docs/img/03-lizard-real-spz.jpg`）。
  **KIRIのPLY取り込みは座標を変換しない**ので、RDFのPLYは回転を付けて使う（KIRI標準の「Rotate for Blender Axes」の回転値は (−90°, 0, −90°) で、どの規約向けかは未確認。今回の実サンプルは −90° X のみで正しく立った）。
- 気づき: SPZ v2は回転のwをxyzから復元するため、wが小さい回転で誤差が大きい（v3で解消された既知の弱点）。復元後に正規化している。

## 4. 描画スパイクの結果

シーン（`scripts/blender/spike_kiri.py`、`scripts/gaussian/make_test_splats.py`）: 合成ガウシアン（市松模様の地面・縞模様の壁・色付き球3つ）と、Blenderメッシュ（立方体・白い床・壁に食い込む球）。
再現: `powershell -ExecutionPolicy Bypass -File scripts/blender/run_spike.ps1 -Exp <basic|relight|calib|shadow_tuned|pointlight|tol|shadow_top|lizard>`。

### 4.1 仕組み（挙動から確認したこと）

KIRIのオフライン描画は、(1) メッシュ側をBlender標準のレンダラー（今回はEevee）でカラーと深度のEXRに描く、(2) ガウシアンをGPUシェーダで描き、メッシュ深度と比較して手前の方だけ重ねる、という2段構え。
ガウシアンはBlenderのレンダラーの一部ではないため、メッシュへの映り込み・GI・屈折にはガウシアンは寄与しない。影だけは専用の近似経路がある。

### 4.2 遮蔽 （`docs/img/03-basic-occlusion.jpg`）

- キューブの後ろの球は隠れ、手前の球はキューブを隠す。壁に食い込んだメッシュ球は壁の手前側だけ見える。
- メッシュの板を地面ガウシアン(z=0)に対して −5cm / 0 / +0.5 / 2 / 5 / 10 / 20cm に置いて真上から見ると、**0cm以上ならメッシュが100%勝ち、−5cmならガウシアンが100%勝った**（深度比較に有意な許容幅はない）。
- ただし浅い角度（グレージング）で見ると、メッシュ面の下2cmにあるガウシアンの地面が縞状に透けた（`03-relight-shadow-montage.jpg` 右上の白い床）。ガウシアンの面とメッシュの面を重ねるときは数cm以上離すか、片方を除く。
- ガウシアンのエッジは柔らかくぼけるため、メッシュとの境界にわずかな暗い縁が出る場合がある。

### 4.3 ライト反応 （`03-relight-shadow-montage.jpg`）

`r2_relight` を有効にすると、シーンのBlenderライト（最大16）の色・強さ・位置にガウシアンの色が反応する。

- 白い太陽（エネルギー3）で、Direct Strength 0.1 / 0.2 / 0.4 のとき、地面の平均RGBは (49,60,27) / (92,112,49) / (176,215,94)。ライト無しの元色は (141,172,76)。**強さにほぼ比例**し、元の明るさ相当は約0.32。
- 橙の太陽では全体が橙に、弱い青の太陽では暗い青緑にシフトし、同じ光でメッシュ（立方体）とも色が揃う。
- 点光源を左右に動かすと、明暗の向きが変わる（球・壁・立方体とも）。
- **明るすぎるとチャンネルごとに飽和して色相がずれる**（白光で赤が桃色、青が水色になった）。強さは必ず較正が要る。
- 方式は「焼き込まれたSH色に、法線とライトから求めた係数を掛ける」。学習時の照明・影が焼き込まれた3DGSでは、**二重にライトがかかる**（元の影の上にさらにライト）。

### 4.4 影 （`03-tol-topshadow.jpg`）

- メッシュ→ガウシアン: `r2_shadows`（Cached Shadows）。立方体の影が地面ガウシアンに落ち、壁に近いメッシュ球の影も壁に落ちた。真上カメラの比較で約1.1万画素が暗くなった。エッジは硬め（既定のフィルタ半径1.5）。
- ガウシアン→メッシュ: `r2_shadow_proxy`（Eevee用の影カード）。球ガウシアンの丸い影がメッシュの床に落ちた。29,814個のカードを作成。上限は「Total Max Cards」で全体共有。
- 影を出せるライトは最大4（メッシュ影）。点光源は6方向の影マップなので重い。
- 未検証: ガウシアン自己影（実験的）、World/HDRIによる拡散照明、Cyclesとの併用。

## 5. 統合とライティング設計への示唆

1. **背景（3DGS）とキャラ・小物（メッシュ／メッシュ由来3DGS）の混在は、Blender側のオフラインレンダリングでは成立する**。前後関係はピクセル単位の深度比較で正しい。
2. **ライトは「焼き込み色への係数」という近似**。背景がWorld Labs由来（焼き込み照明あり）の場合、強い再ライティングは二重照明になる。背景は照明を弱めて（ほぼ焼き込みのまま）使い、キャラ側でライトに反応させる、あるいは背景の光を「ライトで足し引きするムード調整」程度に留めるのが現実的。
3. **影は近似だが、設置感を出すには十分使える**（キャラの影を背景に落とす、背景の木の影をキャラに落とす）。キャラをメッシュで持てばEeveeの影を使い、背景への落とし込みはCached Shadowsを使う。
4. **Unityのゲーム実行環境には、KIRIの仕組みは持ち込めない**（BlenderのGPUシェーダ・Python）。Unity側のライティングは別途設計が必要（aras-p/UnityGaussianSplattingはそのままでは再ライティング非対応）。本スパイクは「見た目の狙いの確認と、オフラインでの検証・参照画像づくり」に使う位置づけにするのが安全。
5. 再現性: KIRIの操作は Python のオペレーター名（`sna.dgs_render_*_<5桁ハッシュ>`）で呼ぶため、**バージョン固定（v5.1.0）が前提**。`scripts/blender/spike_common.py` に包んである。

## 6. 運用メモ・既知の問題

- ヘッドレス実行は `gpu.init()` が必須。`--factory-startup -b --python ...` で、`BLENDER_USER_EXTENSIONS` を専用フォルダへ。
- KIRIの出力ファイル名は `<render.filepath><フレーム番号4桁>_composite.png`（合成時）/ `_color.png`。出力先は絶対パスで渡すこと（相対パスは `C:\` 直下に出た）。
- MCP用Blenderの起動時に `bpy.ops.wm.read_factory_settings()` を呼ぶと、MCPアドオンもKIRIも無効になり接続が切れる。
- WindowsではBlender MCPが使用中のポート（9876）にもbindできてしまい、別のBlenderの接続を横取りする。専用ポート9877を使い、起動スクリプトで9876へのbindを9877へ読み替えている（`mcp_startup.py`）。
- 検証中に私が誤って9876を掴むBlenderを複数起動してしまった。ユーザーに閉じてもらう必要がある（スレッドで報告済み）。
- 画像は `docs/img/03-*.jpg`。生成物（PLY・全レンダー出力）は `experiments/spike/` 以下に出るが、Git管理外。
- カメラ5視点の仮定義は `scripts/gaussian/camera_paths.json`（`spike_common.create_cameras_from_json()` でBlenderカメラ化できる）。今回のスパイクでは未使用。
