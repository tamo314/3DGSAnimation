# 07 Gaussian Frosting（Phase 6 / 参照研究の適用）

実施日: 2026-10-20 / ブランチ: `claude/T7-research` / 環境: WSL2 Ubuntu、torch 2.8.0+cu128、RTX 5060 Ti（sm_120、16GB。他スレッドの学習とGPUを共有）
対象: [Gaussian Frosting](https://github.com/Anttwo/Frosting)（Inria/MPII系の非商用研究ライセンス）。公式コードは `~/ext/Frosting` に置いて**無改変で実行**した（プロジェクトには取り込まない）。課金APIは使っていない。

> 依頼文の参照研究リストでは、Gaussian Frosting のリンクが G-Style のものになっていた。ここでは Frosting 本来のリポジトリ（Anttwo/Frosting）を対象にした。

## 1. 結論

- **最後まで動いたが、今回のデータ（キャラ単体・黒背景・144視点）では、土台メッシュがキャラに収まらず、そのままでは使えなかった。** 公式の推奨設定を試し、前景の範囲指定と可視判定のしきい値も変えて3回実行したが、いずれも土台メッシュにキャラ以外の面（背景の外れ値由来）が大量に混ざった。
- ガウシアン層（100万個）を、素の3DGSの近傍で切り出して統合シーンに置くと、**キャラの形・柄は再現するが、全体に白っぽく霞み、脚や靴が半透明になった**（[図](img/07-frosting-char-medium.jpg)）。素の3DGS・MILo より見た目は悪い。
- **技法の考え方は有望だが、公式コードを使う必然性はない。** Frosting の本質は「メッシュに結びついた細かいガウシアン層」で、メッシュを動かせばガウシアンが追従する（アニメーションに使える）。このプロジェクトには、きれいな Tripo メッシュが**すでにある**ので、抽出メッシュに頼らず、**Tripo メッシュに直接ガウシアンを結びつける自前実装**のほうが筋がよい（7章）。

## 2. 何をする手法か

1. 素の3DGSを学習する（7000反復）。
2. SuGaR 系の正則化（`dn_consistency`: 深度と法線の整合）でガウシアンを面に寄せる粗い段階（15000反復）。
3. 粗いモデルの表面点から Poisson 再構成でメッシュ（土台メッシュ）を作る。
4. 土台メッシュのまわりに、厚みの変わる**ガウシアン層**（Frosting）を作り、最適化する（精錬）。髪・草のような「ふわふわ」ほど層が厚くなる。
5. （任意）テクスチャ付きメッシュの書き出し。

出力のガウシアンは、メッシュの三角形に重みで結びついた表現で、メッシュを変形すると追従する。

## 3. 手順（再現可能）

- 環境: `scripts/wsl/setup_frosting_env.sh`（venv `frosting`。torch 2.8.0、pytorch3d 0.7.8 をソースからビルド、公式の rasterizer・simple-knn をビルド）。
- 1回目: `scripts/wsl/run_frosting_char.sh`（公式の `train_full_pipeline.py`。キャラ単体向けの推奨値 `cleaning_quantile 0`、`connected_components_vis_th 0.5`、100万ガウシアン、低ポリ、短い精錬）。約80分（粗い段階が大半。他スレッドとGPU共有）。
- 2・3回目: `scripts/wsl/run_frosting_char2.sh`（粗い段階は1回目を再利用。`frosting_shim.py` が公式の `train.py` を、粗い段階だけ学習済みで置き換えて実行する。公式コードは書き換えない）。
- 評価: `scripts/wsl/eval_frosting_char.sh`（正解メッシュとの比較）、`crop_frosting.sh`（切り出し）、`scripts/blender/run_scene_char_ply.ps1`（統合シーンで描画）。

## 4. 結果

| 実行 | 設定 | 土台メッシュ | 結果 |
|---|---|---|---|
| 1回目 | 前景範囲は既定、可視しきい値 0.5 | 1,951頂点、範囲 10×14×5 m | キャラ形状が残らず壊れた。ガウシアン層も約1万個しかキャラ表面（2cm以内）になかった |
| 2回目 | 前景範囲をキャラ周り（±0.6 m、高さ-0.1〜1.3 m）に限定、可視しきい値 0.5 | 1,999頂点 | 同じく壊れた |
| 3回目 | 同上、可視しきい値 0.001（実写向け既定） | 144,874頂点（キャラ周りに切り出すと72,397頂点） | キャラ周りの面は得られたが、切り出しても**メッシュ→正解の距離の中央値が約27cm**で、背景由来の面が大量に混ざる。逆に正解→メッシュ（カバレッジ）は中央値5mm |

- 土台メッシュの原因: 抽出の段階で、前景のメッシュ（約680万点）のあとに背景のメッシュ（約71万点）を結合し、「見えない連結成分」を除く処理を行う。キャラ単体＋黒背景では、背景側に大量の面が作られ、前景の判定（しきい値）もキャラの面と背景の面を分けられなかった。公式の想定（実写の風景、または合成の単体物体でも背景がある設定）とデータの性質が違う。
- ガウシアン層（3回目、100万個、PLY 248MB）の法線（最小スケール軸）の精度は、評価できた2.5万個で中央値 26.8°（MILo 10.1°、素の3DGS 26.5°）。平たいガウシアン（flatness<0.3）に限ると 11.8° で、層の平たいガウシアンの向きは面に沿っている。
- 見た目: 層から、素の3DGSの近傍2cm以内の5万個だけを切り出して統合シーンに置くと、**顔・服の柄は再現するが、全体に白っぽく霞み、脚と靴が半透明**になる（[図: 中距離](img/07-frosting-char-medium.jpg)、[図: 正面ワイド](img/07-frosting-char-front.jpg)）。切り出さないと、黒背景由来の黒いもやが背景に残る（切り出しの「近傍」条件は自前）。
- 容量: ガウシアン層は100万個で約250MB。素の3DGS（24万個、約54MB）、MILo（7.3万個）より大幅に重い。ゲーム用途には厳しい。

## 5. つまずきと対処（公式コードは書き換えていない）

MILo・GaussianShader の記録（[07-milo.md](07-milo.md)、[07-gaussianshader.md](07-gaussianshader.md)）と共通のものに加えて:

| 問題 | 原因 | 対処 |
|---|---|---|
| `GaussianRasterizationSettings.__new__() missing ... kernel_size` | 公式の `train_full_pipeline.py` が子プロセスを PATH 上の `python`（別環境）で起動するため、別の rasterizer を読んだ | venv の `bin` を PATH の先頭に置く |
| `No module named 'pytorch3d'` | 同上 | 同上 |
| `torch.load` が `weights_only` で失敗（`numpy.core.multiarray.scalar`） | torch 2.6 以降の既定が変わった | 環境変数 `TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD=1` |
| テクスチャ付きOBJの書き出しで EGL ヘッダーがない | nvdiffrast の GL 版は WSL では動かない | 書き出しを無効化（`--export_obj False`）。今回は不要 |
| 粗い段階だけで約1時間かかる | 15000反復、GPU共有 | `frosting_shim.py` で粗い段階を再利用し、土台メッシュ抽出以降だけ再実行 |

## 6. このプロジェクトへの効き目

| 課題 | 効き目 | 理由 |
|---|---|---|
| キャラのProxy Mesh（アニメーション・衝突判定） | △（考え方のみ） | 抽出メッシュは今回のデータでは使えない。Tripo メッシュが既にある |
| キャラの微細な質感（髪・布のふわふわ） | △ | 層が厚みを持つ設計は合うが、今回は再現が悪化した（霞み・半透明）。短い精錬（2000反復）のせいの可能性があり、未検証 |
| メッシュ連動のアニメーション | ○（考え方） | ガウシアンがメッシュに結びつく設計は、ボーン・スキニングと相性が良い |
| 背景の欠点・照明 | ✕ | 対象外 |

## 7. 自前実装へ持ち帰る候補（推奨）

1. **Tripo メッシュにガウシアンを直接結びつける**: メッシュの各三角形に N 個のガウシアンを置く（重心座標＋法線方向のオフセット、スケールは三角形の大きさに連動）。Frosting の「層」の考え方を、土台メッシュを抽出せずに、きれいな既存メッシュで実現する。メッシュを変形（ボーン）すれば、ガウシアンの位置・向き・スケールが三角形に追従する。Proxy Mesh（アニメーション・衝突判定）と3DGS（表面の描画）を結ぶという、このプロジェクトの Architecture そのものに当たる。
2. **最適化**: 結びつけたまま、色・不透明度・オフセットだけを、Blender で描いた多視点画像（既存のデータセット）に合わせて学習する。ガウシアンの位置は面に拘束されるので、針状スプラットや外れ値は原理的に出にくい。
3. **層の厚み**: 髪・ケープの縁など「ふわふわ」の部分だけ、法線方向の厚み（オフセット範囲）を広げる。
4. 次の一手は、このスレッドではなく、アニメーション実証の側で、Tripo メッシュ＋ボーンで最小の検証（例: 腕を動かしたときにガウシアンが追従するか）を行うこと。
